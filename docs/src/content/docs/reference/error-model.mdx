The node answers a refusal as `{ error: CODE, message, details }` with an HTTP
status. `errorFrom(status, body)` is the one place that becomes an error, and
it matches the status and the code together, never the status alone. Every
typed error extends `CalimeroError`, so `instanceof CalimeroError` and its
`status`, `code` and `details` work for all of them.

| Error | Status and code | Meaning |
| --- | --- | --- |
| `LoginRequired` | `401 UNAUTHENTICATED` | The client's own refresh did not help (or there is no refresh token): sign in again, then repeat. See [Restarts and other nodes](#restarts-and-other-nodes). |
| `WrongNode` | `421 WRONG_NODE` | This node's release may not serve the account, and the client knows no other node that took the request: use another node of the cluster. |
| `NotFound` | `404 NOT_FOUND` | Does not exist for this caller: a missing app and one you may not reach answer alike. |
| `ConfirmRequired` | `412 CONFIRM_REQUIRED` | The request needs a passkey over the challenge in `details`; only reaches you from a method given no passkey. |
| `ConfirmCancelled` | (not from the node) | The user dismissed the passkey prompt. Nothing was sent. |
| `IdempotencyMismatch` | `409 IDEMPOTENCY_MISMATCH` | The key was used before with other arguments. |
| `ReleaseDeadlineError` | `409 RELEASE_DEADLINE` | A release's deadline passed unapproved: no new apps, installs or upgrades until `release` (or newer) is approved. Running apps keep running. |
| `ConsentStale` | `409 CONSENT_STALE` | What a consent page showed changed before the approval; ask for a new request. |
| `ArgsTooLarge` | `413 ARGS_TOO_LARGE` | The call's arguments are over the node's limit (512 KiB); it did not run. |
| `AppError` | `422 APP_ERROR` | The app refused the call: `appCode` (its declared error) and `fields`. The call was logged; its key is spent. |
| `TrapError` | `422 TRAP` | The run trapped: `kind` (`OutOfFuel`, `OutOfMemory`, …). Logged. |
| `UnavailableError` | any `503`, or no answer | After the client's retries: `reason` (`timeout`, `migrating`, `unavailable`, `network`, …), `committed`, `retryAfter`. |
| `CalimeroError` | anything else | `status` and the node's `code`: `FORBIDDEN`, `CONFLICT`, `NOT_INSTALLED`, `NO_REGISTRY`, `BAD_PACKAGE`, `UPGRADE_FAILED`, `INIT_FAILED`, `TOO_LARGE`, `QUOTA_EXCEEDED`, … |

```ts
import { AppError, CalimeroError, UnavailableError } from '@calimero-network/mero-js';

try {
  await client.call(app, 'book', { slot }, `book-${slot}`);
} catch (e) {
  if (e instanceof AppError && e.appCode === 'Taken') showTaken(e.fields);
  else if (e instanceof UnavailableError && e.committed === 'unknown') retryLaterWithSameKey();
  else if (e instanceof CalimeroError && e.code === 'FORBIDDEN') showNoAccess();
  else throw e;
}
```

## Restarts and other nodes

A session token is signed by the node that issued it. Other nodes take it only
while they can vouch for that node's signing key, so when the issuer is
replaced, removed or out of reach (a rolling deploy, an image rollout), they
answer `401` — not because the user signed out. The client answers that
itself:

- **`401 UNAUTHENTICATED`** to a request sent with a session: the client
  refreshes once (`POST auth/refresh`, which any node of the cluster takes) and
  repeats the request once. Requests refused at the same time share that one
  refresh: a refresh token is used once, and a second use would revoke the
  session. Only when the refresh is refused, or the repeated request is refused
  again, does `LoginRequired` reach you. A request made with an API key is not
  refreshed.
- **`421 WRONG_NODE`**: the node runs a mero-tee release the account's owners
  have not approved, so it neither issues nor takes the account's sessions. The
  client moves to the next node given in `nodes` (`new CalimeroClient({ baseUrl,
  nodes, policy })`, each attested under the same policy) and repeats the
  request there once; `client.nodeUrl` names the node in use. With no other
  node, or when the next one refuses too, `WrongNode` (with the node's
  `details`) reaches you: connect to another node of the cluster.

Repeating is safe for any request, a call too: the node answers `401` and `421`
while judging the credential, before it runs anything, and a call keeps its
idempotency key. Two requests are never repeated, because the node refuses them
only after spending something single-use:

- a sign-in or sign-up that answers `421` used its passkey challenge. The client
  moves to the next node and throws `WrongNode`; call `signIn` again.
- a refresh that answers `421` used its refresh token, so it is not sent to
  another node (which would revoke the session). It surfaces as `LoginRequired`
  with `details.refusedWith: 'WRONG_NODE'`, and the next sign-in goes to the
  next node.

## Did it commit?

`UnavailableError.committed` is never a plain boolean:

- `false`: the node says the call did not run (`TIMEOUT`, `MIGRATING`). Its key
  is not spent.
- `'unknown'`: it may have run (a leader change, or a connection that dropped
  before the answer, reason `network`). Send it again with the **same**
  idempotency key: a call that committed is answered from its record.

## Transport errors

Errors of the sealed channel itself are not `CalimeroError`s:

- a policy refusal rejects with a plain `Error` saying which check failed
  (`mock quote refused`, `mero-tee release … is older than the minimum …`, a
  signature or measurement mismatch); nothing is sent to that node;
- `SealedTransportError` (`status`, `code`): the node refused the envelope;
- `StaleTransportKeyError`: from `createSealedFetch` given fixed key bytes,
  when the node restarted.

A body past the sealed cap (64 MiB) is refused in the clear with `413`; the
client reports it as a `CalimeroError` with code `TOO_LARGE`, as the node's own
refusal of a large blob.
