## Follow-up: fix the fixture staleness instead of shipping an error-path-only test

The coordinator asked to replace `tests/e2e/assets/kv_store.wasm` with the ABI-embedded
wasm built from the core branch, and flip the coverage hit to assert the 200 success path.

### What I found before touching anything

The literal ask ("replace `kv_store.wasm`") would not have worked. Tracing the actual
install path:

- `tests/e2e/harness.ts`'s `ensureApplication` and `coverage-sweep.test.ts` both install
  from **`tests/e2e/assets/kv-store.mpk`**, not the loose `kv_store.wasm`. A repo-wide
  grep confirmed `kv_store.wasm` (underscore) is referenced by nothing except this report -
  it's a dead, unused file.
- `kv-store.mpk` is not raw wasm - it's a gzip/tar bundle (`manifest.json` + wasm + a
  sidecar `abi.json`, per core's `.mpk` format). Decompressing the existing one showed its
  internal `kv_store.wasm` **also** lacked the `calimero_abi_v1` section (0 grep matches) -
  the sidecar `abi.json` inside the bundle is a different, older ABI convention that core's
  new endpoint does not read (it only reads the wasm's embedded custom section).
- Per `crates/node/CLAUDE.md`'s bundle-installation gotcha, a `.mpk` install goes through
  `VerifiedBundle`, which checks the manifest's Ed25519 signature and digest-checks every
  artifact against it. So swapping the internal wasm without producing a correctly signed
  manifest would break bundle installation entirely for *every* e2e test that depends on
  kv-store, not just the ABI one.

So the fix had to be: rebuild the actual `.mpk` fixture correctly, not just the loose wasm.

### How I did it

- Found `tools/cargo-mero` in the core worktree - `cargo mero build` (embeds
  `calimero_abi_v1`) then `cargo mero bundle --dev` (packages + signs a `.mpk`).
- The existing fixture's `manifest.json` had `signerId:
  did:key:z6MknF3p5L5FDHJQ7FREUapuX4Wmp4MtF6WrHYaXS2B3eZQd` - which is exactly the
  well-known dev-key signer documented in `tools/cargo-mero/SIGNING.md`. Since
  `ApplicationId = SHA-256(borsh(package, signerId))`, bundling with `--dev` again
  reproduces the *same* signerId and therefore the *same* `ApplicationId` for
  `com.calimero.kv-store` - no identity fork for existing installs/assertions.
- Ran (in the core worktree): `scripts/setup-cargo-mero.sh` to put `cargo-mero` on PATH,
  then `cargo mero bundle --dev` from `apps/kv-store/`. Output:
  `dist/com.calimero.kv-store.mpk`, `signerId: did:key:z6MknF3p5L5FDHJQ7FREUapuX4Wmp4MtF6WrHYaXS2B3eZQd`
  (matches), `package: com.calimero.kv-store` (matches). `appVersion` changed from the old
  fixture's `0.2.11` to `0.0.0` (the workspace's current `[workspace.package] version`) -
  checked no mero-js test asserts an exact kv-store version string (only
  `toBeTruthy()`/`toBeDefined()`), so this is not a breaking change.
- Copied both the newly-built `apps/kv-store/res/kv_store.wasm` (loose file, as literally
  asked, even though unused) and the newly-built `dist/com.calimero.kv-store.mpk` (the file
  that actually matters) into `tests/e2e/assets/`, replacing the stale ones. Verified
  `grep -a -c calimero_abi_v1` returns 1 on the new loose wasm.

### Coverage test update

Replaced the single error-path test with two, matching the coordinator's spec:

```ts
it('returns the embedded ABI manifest', async () => {
  const abi = await mero.admin.getApplicationAbi(applicationId);
  expect(abi.schema_version).toBe('wasm-abi/1');
  expect((abi.methods as unknown[])?.length).toBeGreaterThan(0);
});

it('rejects an unresolvable service_name with a 400 naming the parameter', async () => {
  await expect(mero.admin.getApplicationAbi(applicationId, 'bogus')).rejects.toMatchObject({
    status: 400,
    bodyText: expect.stringContaining('service_name'),
  });
});
```

Used `.rejects.toMatchObject({ status, bodyText: expect.stringContaining(...) })` rather
than a manual try/catch - matches the `error.status` / `error.bodyText` shape already
asserted elsewhere (`tests/e2e/auth-api.test.ts:171-172`), just via the cleaner
`.rejects` form already used throughout this file, and stays robust to the exact error
string per the coordinator's ask (asserts only that it names `service_name`).
